# 古韵AI 跨校协同手册

> 适用：2026 参赛期内，与其他学校同学协作开发 / 文档 / 测试
> 编制：2026-09-14 · 依据《2026 参赛手册》第 8 条

---

## 一、规则依据（手册第 8 条原文摘要）

- 参赛对象：在校研究生 / 本科生 / 高职高专学生，专业不限
- 组队：**每支参赛队 1–5 名学生 + 1–2 名指导教师，** ***可跨校****
- 报名：以学校为单位；参赛院校安排职能部门负责真实性 / 规范性审核
- 大赛只接受以学校为单位组队参赛（**核心**：多校学生 = 同一支队伍，向牵头校报名）

**关键结论**：跨校协同在规则上完全允许，但报名主体必须落到牵头校。各校学生通过同一支队伍参赛，**对外是一个作品编号**，对内按本文档分工。

## 二、推荐组织结构

```
[牵头校]  队长 1 人      —— 总负责、报名系统管理员、对外答辩
[成员 A 校]  队员 N 人  —— 各自负责的模块
[指导教师 1~2 名]        —— 跨校成员各自的指导老师，分别负责本校内容审核
```

典型 4 人队伍（跨 2 校）：

| 角色 | 人数 | 校属 | 职责 |
|---|---|---|---|
| 队长 / 答辩 | 1 | 牵头校 A | 总负责、报名、答辩、对外材料 |
| 后端 / 算法 | 1 | A 或 B | 提示词工程、格式校验算法、LLM 联调 |
| 前端 / 桌面 | 1 | A 或 B | React + Electron + MiniMax 跳转集成 |
| 文档 / 测试 | 1 | A 或 B | SRS、设计文档、演示视频、e2e 测试 |

## 三、代码协同：Git 远程仓库

### 3.1 建仓库（队长执行一次）

推荐平台（任选）：

| 平台 | 优点 | 缺点 |
|---|---|---|
| **Gitee** | 国内速度、稳定、私有仓库免费 | 多人协作需企业版（一般 5 人以下免费够用） |
| GitHub | 生态最好、CI/Action 免费 | 国内访问偶发慢 |
| GitCode（CSDN） | 国内、开源 | 生态较小 |

示例（**Gitee**）：

1. 队长在 Gitee 创建私有仓库 `guyun-ai`（README、.gitignore 选 Python + Node）
2. 本地推送：
   ```bash
   cd G:\cunchu\大学\作业\AI音乐
   git remote add origin https://gitee.com/<队长账号>/guyun-ai.git
   git push -u origin master
   ```
3. 在 Gitee 仓库「成员管理」添加协作者（其他队员的 Gitee 账号），**权限：Developer**（可推送 develop 分支）
4. 把仓库地址发给所有队员

### 3.2 队员克隆

```bash
git clone https://gitee.com/<队长账号>/guyun-ai.git
cd guyun-ai
npm install              # 根目录
cd backend && python -m pip install -r requirements.txt && cd ..
cd frontend && npm install && cd ..
```

### 3.3 分支策略（Git Flow 简化版）

比赛周期短（6 天冲刺），用最简分支：

| 分支 | 用途 | 谁推 |
|---|---|---|
| `master` | 已验证可跑的稳定版 | **只有队长**（merge PR 后推） |
| `develop` | 日常开发主分支 | 全员 |
| `feat/<模块>` | 单个特性 / 修复 | 各自创建 → PR → 队长审核 merge |
| `hotfix/<问题>` | 紧急修复 | 各自创建 → PR → 队长立即 merge |

**规则**：
- 任何改动都从 `develop` 切 `feat/xxx` 分支开发
- 完成后提 PR，**PR 标题用中文**，描述改了什么 + 怎么测的
- 队长在 Gitee 网页审核 → 无问题 merge 到 develop
- 阶段性验证（如端到端跑通、当日演示通过）后，队长把 develop 合并到 master
- **参赛周期结束后，git log 就是完整的创作时间证据**（一票否决项之"非本届周期原创"防线）

### 3.4 提交规范

```bash
git config core.quotepath false        # 中文文件名不转义
git config i18n.commitEncoding UTF-8
git config i18n.logOutputEncoding UTF-8
git config user.name "你的姓名"
git config user.email "你的邮箱"
```

提交信息格式（**用中文**）：

```
<类型>: <一句话总结>

【背景】为什么要改
【改动】具体改了什么
【测试】怎么验证
【影响】对其他模块的影响
```

类型：`feat` / `fix` / `refactor` / `docs` / `test` / `chore`

示例：
```
feat: 步骤 3 添加 MiniMax 一键打开按钮

【背景】用户希望提示词包生成完毕能立即在 MiniMax 创作页使用
【改动】在 ExportStep 右栏 MiniMaxSteps 卡片顶部加主按钮
       新增 frontend/src/utils/external.ts 跨端工具
       electron/main.js 注册 IPC + preload 暴露 openExternal
【测试】手动验证：复制 → 打开 → 浏览器态与桌面态都正常
【影响】不影响主流程
```

### 3.5 跨校网络小坑

- 校外推 Gitee 偶发失败 → 重试 / 切移动热点
- 大文件（视频、PDF）**不要**塞进 git 仓库，用 Gitee Release / 百度网盘 / 微信群文件分发
- gitignore 已配好 node_modules / .secrets.json / *.db

按手册附件 1-5 拆分给不同队员：

| 文件 | 负责人 | 工具 |

## 五、演示视频协同

演示视频（≤ 8 分钟）需要：
- 录制软件：OBS Studio（开源、跨平台）
- 分镜：队员 A 录主流程，队员 B 录后端 + 校验 + MiniMax 跳转
- 后期：剪映 / Premiere 合并

**脚本建议**（按手册 65% 技术分评分点 1:1 映射）：

| 时间 | 镜头 | 对应评分点 |
|---|---|---|
| 0:00-0:30 | 作品介绍 / 选题 | 10% 选题定位 |
| 0:30-2:00 | 流程演示：创意 → 元标签 → 歌词 → 导出 | 创作技能「提示词精度 + 人工干预」 |
| 2:00-3:30 | 格式校验算法解释 | 创新性「原创算法」 |
| 3:30-5:00 | MiniMax 跳转 + 真实 mp3 试听 | 跨平台协同 |
| 5:00-6:30 | 版本管理后台展示 | 创作技能「多智能平台协同 + 人工干预度」 |
| 6:30-7:30 | 安全 / 部署 / 文档 | 15% 技术规范 |
| 7:30-8:00 | 团队与未来 | 10% 展示答辩 |

## 六、答辩协同

### 6.1 谁上答辩台

- 队长：主讲（控制时间、回答技术问题）
- 队员 A：演示（操作现场跑一遍主流程）
- 队员 B：候补回答（专项问题）

### 6.2 答辩高频问题预案

| 问题 | 参考答案 |
|---|---|
| 为什么不用 Suno/Udio？ | 不可控 + 不可审计；本作品定位是「可控的提示词工坊」 |
| 「以原创算法为核心」体现在哪？ | minimax.py 格式校验器：14 标签 / 中文→英文映射 / 字数 / 6 项元标签完整性 |
| 人工干预充分的证据？ | 全链路版本管理：original / ai_optimized / human_modified / restored 四类 |
| 算力要求？ | CPU 即可；仅 LLM 走云端；GTX 1650 完全够用 |
| 为什么用 DeepSeek 而不是更大的模型？ | Pro 强推理 + Flash 性价比；统一 OpenAI 兼容协议；中文能力稳定 |
| 知识产权如何处理？ | 全部素材自制或使用 CC0 许可；SoundFont 用许可明确的 |

## 八、风险与应急

| 风险 | 应对 |
|---|---|
| 队员失联 / 退出 | 队长接住核心模块 + 联系指导教师 |
| Gitee 仓库被封 / 限速 | 切 GitHub 镜像 + 微信群文件兜底 |
| LLM 临时不可用 | 后端 LLMServiceError → 前端提示重试 + 切换 DeepSeek Pro/Flash |
| MiniMax 会员失效 | 走本地兜底管线（legacy/）—— 比赛前确认会员状态 |
| 演示现场网络差 | 提前下载 mp3 备份 + 录屏兜底 |
| 答辩前电脑故障 | U 盘备一份 EXE + PDF + 视频；可用队员的电脑临时顶上 |

## 九、参赛周期证据策略（重要）

手册附件 5「否决指标」中有一条：「不在参赛时间段内设计的作品」是直接否决项。

**git 提交历史就是最硬的证据**：
- 仓库必须在 2025-10-01 ~ 2026-09-20 期间有真实提交
- 提交时间戳由 git 自身管理，无法事后伪造
- 队长每周导出一次 git log → 存档到 `文档/创作周期证据/`

```bash
# 队长每周日执行
git log --since="2025-10-01" --until="2026-09-20" \
  --pretty=format:"%h | %ad | %an | %s" \
  --date=iso > 文档/创作周期证据/git-log-$(date +%Y-%m-%d).txt
```
